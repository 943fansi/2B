# 显存估算方法

> 这张表的所有 `peak_vram_est_gb` 都是**估算**。本文说明估算怎么来的、哪里会偏、怎么用实测校准。

---

## 一、为什么"权重体积"不能当判据

以 MiniCPM-OCR 1.0 为例：

| 项 | 体积 | 说明 |
|---|---|---|
| LLM Q8_0 | 0.812 GB | 语言主干 |
| mmproj (视觉投影) f16 | 0.901 GB | **必须一起加载** |
| 小计（权重） | 1.71 GB | 这就是"GGUF Q8 约 1.7GB"的来源 |
| KV Cache @8K ctx | ~0.09 GB | Qwen3.5 混合架构，只有 6 层需缓存 |
| 视觉激活（单页 A4） | 0.8–1.5 GB | 随分辨率/切块数增长 |
| 框架开销 | 0.45 GB | CUDA context + workspace + 碎片 |
| **实际峰值** | **3.0–4.4 GB** | |

权重 1.71GB，峰值 3.0–4.4GB，**差 1 倍以上**。这就是为什么只看权重的表会得出"极充裕"的错误结论。

---

## 二、公式

```
峰值 = 权重 + KV + 激活 + 框架

权重  = 参数量 × bytes_per_param
        BF16/F16 = 2.0   FP8/Q8 = 1.0   Q4 = 0.5

KV    = 2 × L_eff × H_kv × D_head × bytes × T × B
        L_eff = 实际缓存 KV 的层数（混合线性注意力模型远小于总层数）
        T     = 序列 token 数（含视觉/音频 token！）
        B     = 并发序列数

激活  ≈ 经验系数 × 参数量（本文按任务类型取 0.15–0.5）
        多模态任务真实值由输入尺寸主导，经验系数只是下限

框架  ≈ 0.45 GB（CUDA context 约 0.3–0.4GB + cuBLAS workspace + 显存碎片）
```

### 关键：vLLM 的预分配

vLLM / SGLang 启动时按 `gpu_memory_utilization`（默认 **0.9**）预先把显存划进 KV 池。
这意味着**即使模型只要 2GB，vLLM 也会把 7.2GB 占满**，与别的进程不能共存。

脚本对含 vllm/sglang 的部署栈统一乘 `1.15` 系数，代表 CUDA graph 与预分配的额外开销。
实际部署请显式传参：

```bash
--gpu-memory-utilization 0.75 --max-model-len 8192 --max-num-seqs 4 --enforce-eager
```

## 三、多模态模型的特殊之处

OCR / ASR / TTS 的显存不由参数量主导，而由**输入规模**主导：

| 任务 | 显存主要变量 | 典型放大倍数 |
|---|---|---|
| OCR | 图像长边像素、切块（tile）数 | 权重 × 1.5–2.5 |
| ASR | 音频时长（编码器序列长度） | 权重 × 1.2–1.8 |
| TTS | 生成长度、streaming 分块 | 权重 × 1.4–1.6 |
| Embedding | batch size、序列长度 | 权重 × 1.0–1.4 |

**所以"极充裕"这种结论在多模态模型上基本不成立**——同一个模型处理一张 A4 和处理一张 A3 报纸，峰值可以差一倍。

## 五、怎么用实测校准

Phase 1 的任务就是用真实数字覆盖估算值。统一测量模板：

```python
import torch, subprocess, json

def peak_gb():
    torch.cuda.synchronize()
    return torch.cuda.max_memory_allocated() / 1024**3

def smi_gb():
    out = subprocess.check_output(
        ["nvidia-smi", "--query-gpu=memory.used", "--format=csv,noheader,nounits"]
    ).decode().strip().splitlines()[0]
    return float(out) / 1024

torch.cuda.reset_peak_memory_stats()
# ... 推理 ...
print(json.dumps({
    "torch_peak_gb": round(peak_gb(), 2),   # PyTorch 分配器视角
    "smi_used_gb":   round(smi_gb(), 2),    # 驱动视角（含 context 开销）
}))
```

两个数都要记：`torch_peak` 少了 CUDA context，`smi_used` 含其他进程，**真实上限看 `smi_used`**。

## 六、已知偏差方向

| 偏差源 | 方向 | 影响 |
|---|---|---|
| 激活经验系数 | **低估** | OCR/ASR 高分辨率/长音频时可能低估 30–50% |
| KV 的 `L_eff` 假设 | 双向 | 混合架构层数未公开时只能猜 |
| vLLM 预分配 | **低估** | 默认 0.9 时实际占用远高于模型需求 |
| 官方最低显存 | **已覆盖** | 存在 `hard_min_vram_gb` 时直接取 max |
| CUDA context | 双向 | 驱动版本不同可差 100–200MB |

**结论：本表适合用来"排除明显不行的"，不适合用来"确认一定能跑"。** 能不能跑，只有实测算数。
